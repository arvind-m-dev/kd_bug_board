
## BugFlow architecture
- Use shared frontend confirmation and error feedback for sign-out and portal access changes; keep failed confirmations open and offer retry for failed reads so actions remain recoverable without altering server authorization.
- Workspace routes use a shared server-session beforeLoad check and redirect to the standalone login page before rendering; member token routes keep their own scoped access validation.
- Admin cookies are Secure, HttpOnly and partitioned with SameSite=None for embedded preview support; mutations retain same-origin validation and sign-in verifies session readback before navigating.
- Preserve TanStack Start file-based routes and shadcn controls; all content routes carry their own metadata for reliable navigation and previews.
- Keep pure domain rules in `src/lib/bugflow.ts` and `src/lib/bug-workflow.ts`, presentation in `src/components/bugflow`, and server-only integrations behind server functions; this separates permission/count rules from UI.
- Unconfigured views display unavailable data, never fabricated records or success; live features require approved development connections.
- Keep proposed Neon schema changes in versioned SQL files under `database/` and apply them to the Neon database referenced by DATABASE_URL; this makes database changes reviewable and keeps credentials out of app code.
- AI onboarding uses a server-only call to an OpenAI-compatible API (AI_API_KEY) and verifies a live Neon Admin session before spending credits; only an authorized atomic member save grants selected role-limited permissions and actual project scope, never generated guidance.
- Admin sign-in verifies configured email and password only on the server and maps the verified owner to expiring hashed sessions in Neon; member links use hash-only validation plus server-encrypted recovery for Admin copying, and are validated for role, active user, expiry and revocation on every read.

- Bug reports and changes use shared scoped server functions for Admin and member panels, validate active access and explicit permissions, and atomically write immutable actor history; optimistic versions and request IDs protect retries and concurrent edits.

- Member lifecycle uses soft deletion and atomic audit records, retaining bug references while revoking all member portals; welcome acknowledgements live on the validated portal so first-visit behavior persists across devices.
- A shared theme provider updates semantic CSS variables and saves only the theme preference in browser storage; all workspace and member pages use the same theme controls.
- Single-project forms retain scoped IDs while hiding redundant selectors; compact tables omit project columns without changing server authorization.

- Shared report validation derives omitted titles and actual results from the submitted description; contextual facts remain empty to avoid invented data.
- Expanded bug rows reuse the shared report presentation and scoped detail query; inline assignment uses the existing authorized audited mutation.
- Settings uses the shared scoped workspace query for option and assignee management; member creation invalidates member, workspace and detail queries so eligible assignment choices refresh immediately.

- An MCP server at `/api/mcp` lets any AI client read and report bugs using a Bearer AI token scoped to one panel (Admin or a member); tokens are hashed in `bugflow.ai_tokens`, resolved by the `'ai'` access kind through the same scoped server functions as the app, and `checkOrigin` no-ops outside the Start request runtime because MCP calls carry no cookie. No delete tool is exposed. claude.ai/ChatGPT connect over OAuth 2.1 + PKCE (`/api/oauth/*` and `/.well-known/oauth-*` in `src/server.ts` → `oauth-routes.server.ts`); the consent sign-in reuses the Admin unlock or a member portal link, auth codes are single-use and hashed (migration `017`), and the issued access token is a `bugflow.ai_tokens` row so OAuth connections are revocable in Settings → AI access. MCP tools answer in compact text, not JSON, to keep AI reading cheap.
- AI tokens expire after 90 days without use (migration `026`, `expires_at`; each MCP use pushes it out again in the same resolve statement, `AI_TOKEN_IDLE_DAYS` in `src/lib/ai-tokens.ts`). `source` separates hand-made tokens (member limit 10 live) from OAuth connections; an OAuth exchange keeps only the newest 10 per panel, revoking older ones under a per-panel advisory lock and auditing `ai_token.oauth_limit` in the same statement.
- Timed video marks live on `bugflow.bug_media.marks` (migration `018`) as frame-relative shapes with start/end seconds and an optimistic `marks_version`; `saveVideoMarks` checks upload permission and writes the audit row in the same statement. The recording is never re-encoded; `VideoPlayer` (`video-marks.tsx`) draws marks over playback for every viewer.
- Uploads run in a tab-wide queue (`media-queue.ts`) so reports can be submitted while recordings compress; background files show in the uploads tray. MP4/MOV files get a browser-side faststart (`mp4-faststart.ts`) and signed view links are stable per 5-minute window so the browser cache is reused.
- Removing a single file moves it to the Trash for 30 days (`bug_media.restorable_until`, migration `019`): the media sweep purges only rows whose window is null or past; restore/delete-forever are available to the uploader or Admin from My media and the Admin Trash.
- Media viewing is view-only for everyone. Mark-up is only for the uploader: on the local file in the upload queue, or on their own files from My media in the member portal (`upload-markup.tsx`; images get a marked-up copy): images are replaced by the marked-up version, recordings carry timed marks saved right after attach (`saveVideoMarks` accepts only the uploader). Bug panels stage files until "Upload" for that reason.
- Each image/recording uploads a small JPEG preview to `<key>.thumb.jpg` (`has_thumb`, migration `020`); lists show previews and never load video data. Recordings over ~5 Mbps are re-encoded (MP4 preferred) before upload so they stream quickly.
- The notification bell skips file events (`bug.media_*`, `QUIET_ACTION_PREFIXES` in `notifications.ts`); they stay in the activity log and on each bug.
- Signed-out `/admin*` visits redirect to `/login?redirect=<path>` (same-site paths only, `safeReturnPath`); an Admin session that ends mid-use (`isAdminSessionError`) clears caches and returns to sign-in. Admin password checks (sign-in and OAuth consent) are throttled per client address.
- Links meant for other people use `shareOrigin()` (`VITE_SITE_URL` when copied on localhost) and warn when still local. Uploads go browser → bucket, so the bucket CORS rule must list every app address; Settings → Media storage → Test runs the browser's preflight per address (`corsBlockedOrigins`).
- Bug report edits are version-checked in one statement that also writes the audit row; detail/step writes depend on that row. Non-Admin edits cannot change priority or severity.
- Bug codes (migration 024): display code = `bugs.code_prefix` + padded number (`formatBugCode(id, prefix)`); prefixes are Admin-managed in dropdown options (`prefixes`, first = default for new bugs), stamped at report time and immutable except by Admin edit (audited). The numeric id stays the identity everywhere (MCP, sprint add, URLs).
- Phase 2.4 backlog (migration 023): stories/tasks/epics are `bugs` rows (`kind`, default 'bug') flowing the SAME 13-status workflow; `parent_id` (epic holds anything, story holds tasks; cycle-checked), `estimate`, `ready`, `backlog_rank` (fractional string, `rankBetween` in `src/lib/backlog.ts` — a reorder writes one row). The workspace bug lists/counts/exports/MCP filter `kind='bug'`; epics are refused by `addToSprint`. Backlog writes are Admin-gated and audited (`backlog.*`; rank changes quiet).
- Phase 2.3 board: `/admin/board` is a view over the 13-status workflow — columns in `src/lib/board.ts` (`BOARD_COLUMNS`, every status in exactly one column, tested). A drop runs `dropAction`: exactly one allowed plain transition → direct `updateBug` status change; assign/verify/ambiguous-close → open the bug (never guessed); otherwise refused and the column dims. Native drag + per-card Move menu (deliberate deviation from plan D5 `@dnd-kit`). Resolution still only via verify.
- Phase 2.2 sprints (migration 022): `sprints` (one `active` per project, partial unique index) and `sprint_items` (membership history with `removed_at` and `carried_from_sprint_id`). Pure rules in `src/lib/sprints.ts` (`maySprint`, `canChangeSprintState` plan→active→closed, `summarizeSprint`), server in `sprints.server.ts` (Admin-gated, audited as `sprint.*`; `sprint.item_*` are quiet in the bell). A bug is in at most one open sprint, checked in `addToSprint`. Admin-only so far (`/admin/sprints`); member planning/MCP pending.
- Phase 2.1 due dates (migration 021): `bugs.due_on` is an optional plain date. "Overdue" is derived, never stored — a bug is overdue when `due_on` is before today (in the workspace time zone, settings key `workspace.timeZone`, default UTC) and the status is not closed (`CLOSED_STATUSES` in `src/lib/bugflow.ts`). Only `plan` holders (Admin always; QA preset) may set or clear a date (`maySetDue`); the value is dropped on report and ignored on edit for anyone else. The change is audited inside the existing `bug.edited` action. Overview overdue count comes from SQL; the list filter is client-side over the loaded page, matching the other filters.
- Review hardening (migration 025 adds per-bug child indexes): browser server functions validate `clientAccessSchema` (Admin/portal only) — AI tokens resolve only through `/api/mcp`. Replacing or revoking a portal link revokes its AI/OAuth tokens. OAuth redirect URIs must be https (http only for loopback) and the consent page names the redirect host and cannot be framed. Sprint/backlog writes use `audited()` (`audit.server.ts`) so the audit row is in the same statement; `addToSprint` takes a per-bug advisory lock. Bug references parse any prefix via `parseBugRef`; dates use `isCalendarDate`; CSV cells pass `neutralizeFormula`. Member sprint views list only bugs the panel may see (counts still cover the whole sprint).
- Jira CSV export (`src/lib/jira-csv.ts`, pure, tested; UI `jira-export.tsx`): the Download dialog offers Excel or Jira CSV, and the bug list's selection bar exports ticked bugs ("Select all N" covers every page of the current filters). `exportBugs` accepts `ids` and returns file names; reporter/assignee emails are added for Admin only so member exports never reveal teammates' emails. Files appear as in-app links in each Jira description (never public bucket URLs); no BOM so Jira reads the first column; dates use `JIRA_DATE_FORMAT`.
- Full e2e suite (`npm run test:e2e:full`, `e2e/full/`, `playwright.full.config.ts`) drives every portal through the UI and writes data: it runs against the `.env.local` database (demo data) on a built server at port 4799, names every record `E2E-<area>-…`, cleans up after itself, and never saves workspace-wide settings. Test output stays outside the repo (git-ignored).
- Jira Cloud connection (Phase 3 Gate 1, migration `027`; connection only — no bug is synchronized yet): one live `bugflow.jira_connections` row per workspace because one Atlassian grant holds one rotating refresh token. Atlassian OAuth 2.0 (3LO) with a hashed, single-use `state` bound to the Admin session that started it (PKCE is not part of Atlassian's flow). Tokens are AES-GCM ciphertext under `JIRA_TOKEN_ENCRYPTION_KEY`, bound to the row id and purpose (`src/lib/jira/crypto.server.ts`). Refresh is a lease plus a generation compare-and-swap (`jira/refresh.ts`, pure, tested) since Neon over HTTP cannot hold a lock across the call to Atlassian. Admin operations are server functions (`jira/jira.functions.ts`) so they keep `requireAdmin`/`checkOrigin`; only routes a third party calls are raw (`/api/integrations/jira/callback` → `jira/routes.server.ts`, Admin session read with `adminSessionFromRequest`). Nothing is saved, and no state is called connected, before a live read from Jira; `JIRA_ALLOWED_SITE_URL` pins the only connectable site. Separate from the AI MCP/OAuth feature; `scripts/jira-spike.mjs` is the stand-alone contract check.
- Jira outbound sync (Phase 3 Gate 2, BugFlow → Jira; built against a fake Jira, not yet run against a live site): every bug write (`reportBug`, `changeBug`, `editBugReport`, `deleteBugReport`, Trash restore) adds a `bugflow.jira_outbox` row in the same statement/transaction through `src/lib/jira/outbox-entry.server.ts`, and only when `jiraOutboxOn()` finds the Jira tables — a database without migration `027` must keep working, so never reference `bugflow.jira_*` from a bug write without that guard. A row is only a "this bug changed" marker (one waiting per bug); `processor.ts` decides the work from the current bug, the current Jira issue and the two snapshots on `jira_issue_links` via the three-way rules in `compare.ts` (push / pull / ack / conflict — never newest-wins). Pure rules live in `mapping.ts`, `adf.ts`, `compare.ts`, `processor.ts` (ports `JiraPort`/`SyncStore`/`OutboxQueue`, tested with fakes); Neon and HTTP live in `outbox.server.ts` and `issues.server.ts`. Status is compared in Jira's status space and moved only by one available Jira transition; description parts holding Jira formatting are never rewritten from plain text (conflict instead); creation is made repeat-safe by a `creating` link row, a per-attempt label (`bf-<bug>-<8 hex>`) and a 90 s settle before searching. `POST /api/internal/jira/process` runs one bounded pass and accepts only `Authorization: Bearer <JIRA_JOB_SECRET>` (never cookies). Sync bookkeeping (`jira.created`, `jira.exported`) is attributed to the non-login Jira Sync user, is excluded from a bug's "last change" and from member history, and never reaches the bell.
- Jira project mapping: `src/lib/jira/mapping.server.ts` (`jiraResources`, `jiraProjectShape`, `saveJiraMapping`, `previewJiraMapping`, `activateJiraMapping`, `pauseJiraMapping`, exposed as Admin server functions in `jira.functions.ts`) with pure rules in `discovery.ts` (reply schemas taken from Atlassian's published REST v3 description, `suggestConfig`, `shapeProblems`). Everything listed is a live Jira read; a mapping is a `draft` until it passes `configProblems` + `shapeProblems` against the live project at activation, an active mapping is never edited in place (pause first; a paused one keeps its Jira project and issue type), and activation sends nothing by itself. Priorities are read from the Bug type's create metadata because `priority/search` needs a scope this app does not request. Do not wrap a statement that already has data-modifying CTEs in `audited()` (Postgres rejects a nested data-modifying `WITH`); write the audit CTE at top level as `saveJiraMapping` does.
- Jira inbound and the shared pass (Phase 3 Gates 3–5, built against a fake Jira; never run against a live site — `docs/JIRA_CONNECT_STEPS.md` lists what that leaves unproven): whichever side a queue row came from, `processor.ts` runs the same `pass` for the pair — BugFlow-only changes are pushed, Jira-only changes are pulled, equal ones acknowledged, different ones become a conflict — so there is no separate "inbound engine" to keep in step. What a Jira change may do is decided by the pure rules in `inbound.ts` and nothing else: text within BugFlow's own limits, status only along the 13-status graph via `statusPath` as the non-login `JIRA_ACTOR` (never `RESOLVED` except from `RECHECK` with `inbound.resolveFromRecheck` on, recorded as a verification; never `ASSIGNED` by status; one hidden "start work" step only for an assigned bug), assignment only for an Admin-confirmed member who is on the project. `inbound.server.ts` is the integration's own write path (version-checked, request ids from `ids.ts`, the same history rows as a person's change, actor = Jira Sync); it never calls a browser server function and never builds an `access` object. Imports are one atomic statement with a request id derived from connection + immutable issue id. Do not add a second way for Jira data to reach `bugflow.bugs`.
- Jira queues: `jira_outbox` (bug changed) and `jira_inbox` (issue changed, small envelope only — the issue is always re-read) are leased under ONE advisory lock (`CLAIM_LOCK`) with cross-queue exclusion, so a bug and its issue are never worked on from two sides at once. `POST /api/integrations/jira/webhook/:connectionId` authenticates Atlassian's HS256 bearer token (algorithm fixed on our side) and only stores; `POST /api/internal/jira/process` and `/reconcile` (Bearer `JIRA_JOB_SECRET`) run `jobs.server.ts`. Reconciliation (`reconcile.ts`) only queues: an overlap-safe relative-time JQL scan, BugFlow changes with no outbox entry, links unseen for a day, and webhook registration/renewal (https origins only; on http the scan is the whole sync). An Admin's conflict decision is stored in `jira_issue_links.overrides` (`push` / `pull` / `held`) and carried out by the next pass through the same rules; an unlinked pair (`disabled`) is never re-created or re-imported.
- Jira sprints and estimate: synchronized through the issue's own Sprint and story-points fields (`config.sprintField` / `estimateField`, detected by Jira's field type in `discovery.ts`), which needs no Jira Software scope. Jira owns sprints: `sprints.server.ts` mirrors those seen on synchronized issues into `bugflow.sprints` + `jira_sprint_links`, keeping BugFlow's invariants (one active sprint per project, no reopening, closing never carries over). BugFlow's own sprint add/remove/close and backlog estimate changes add an outbox marker in the same transaction (`outboxMarker`, `outboxSprintMarkers`), guarded like every other bug write.
- Jira Admin surface: `admin.server.ts` (overview, `resolveJiraConflict`, `retryJiraParked`, `syncJiraNow`), `people.server.ts` (member ↔ Atlassian account, Admin-confirmed only), screens in `src/components/bugflow/jira-sync.tsx` with wording from `labels.ts`. Anything listed from Jira is a live read; a failed read shows the error and a retry, never a remembered or invented list.
- Database checks (`npm run test:db`, `scripts/db-check.mjs`, `vitest.db.config.ts`, `src/test/db/*.dbtest.ts`): each suite runs the real `.server.ts` code against its own fresh database on a throwaway local Postgres (127.0.0.1, random port, temp folder, deleted afterwards) with `neon.server` replaced by `pg` and the session module by a fixed Admin. They never read `DATABASE_URL`. A suite named `without*` gets every migration except `027`, which is how "bug writes still work without the Jira tables" stays proven. Add a suite here whenever a change adds or alters SQL.
