# Bug Board — Phase 2 & 3 plan

Date: 2026-10-28 · Status: **Proposed, not started** · Branch base: `main`

Source of scope: `Bug_board_marketing_media/site/bugflow-guide.html` §17 and that folder's `CLAUDE.md`. Phase 1 (core bug board) is delivered; see `docs/FEATURES.md`.

## Goal
Make Bug Board the place where bug fixing is planned and delivered, not only recorded: dates, sprints, a board for stand-ups, a backlog that holds stories and tasks next to bugs, and a guide so new people start on day one.

## Decisions (agreed 2026-10-28)
| # | Question | Decision |
| --- | --- | --- |
| D1 | Jira sync? | **No Jira sync or import at all.** Not in Phase 2 or Phase 3. Backlog and sprints are native. (Marketing `CLAUDE.md` still mentions "Jira two-way sync"; correct it there.) |
| D2 | Stories/tasks/epics: same table as bugs or a new table? | **Same table** with `bugs.kind`. Portals, scope, media, comments, history, MCP and exports keep working with no duplication. Non-bug kinds get a short workflow (below). |
| D3 | Who plans sprints and sets due dates? | New permission **`plan`**: Admin always; added to the `qa` preset; grantable per member. |
| D4 | Date basis for "overdue" | One **workspace time zone** in Settings (default: Admin's browser zone at first save). Due dates are plain dates, overdue from the next day in that zone. |
| D5 | Drag-and-drop library | ~~`@dnd-kit`~~ → built 2026-10-29 with **native HTML drag + a per-card Move menu** (keyboard path): the codebase already uses native drag (dropdown options), so no new dependency. |
| D6 | Reminders channel | **In-app only** (notification bell) in Phase 2. Email/Slack/Teams in Phase 3. |

## Rules every step follows (from `AGENTS.md`)
- Pure rules in `src/lib/bugflow.ts` / `src/lib/bug-workflow.ts` with unit tests; UI in `src/components/bugflow`; DB access only in server functions.
- Every write goes through the shared scoped server functions: active access + explicit permission check, version check, request ID, and the audit row **in the same statement**.
- Scope never widens: members only see sprints/board items for projects in their portal scope.
- Unconfigured or empty data shows an empty or unavailable state, never sample numbers.
- New SQL as `database/021_…` onward, idempotent, applied to the Neon DB in `DATABASE_URL`. Never edit an applied file.
- Each new route has its own metadata (`pageHead`), and Admin routes use the shared session `beforeLoad`.

## 2.1 Due dates
**Data — `021_due_dates.sql`**
- `bugs.due_on date null`; index `(project_id, due_on) where deleted_at is null`.
- `settings` key `workspace` gains `timeZone` (no new table).

**Rules (`bug-workflow.ts`)**
- `isOverdue(bug, today)`: `due_on < today` and status not in closed set (RESOLVED, NOT_A_BUG, DUPLICATE, WONT_FIX).
- `dueSoon(bug, today)`: due today or tomorrow, not closed.
- `maySetDue(access)`: Admin or `plan`.

**Server**
- Extend `editBug` (version-checked, audited) with `dueOn`; audit action `bug.due_changed` (old → new).
- List/filter params: `due=overdue|soon|none|range`.

**UI**
- Due date field on report/edit (only shown to `plan` holders). Badge in rows: red "Overdue 3d", amber "Due tomorrow".
- Overview card **Overdue**, opening the filtered list (same count definition as the list).
- Calendar view (`react-day-picker`, already installed) on All Bugs: month grid, a day opens that day's bugs.
- Notification bell: "due tomorrow" and "now overdue" for assignees and the reporter, computed on read from `notification_state`. No background job.

**MCP:** due date and overdue flag in compact list/detail text; `list_bugs` accepts `due=overdue`.

**Done when:** setting, changing and clearing a date is audited; overdue count = filtered list length; members outside scope see nothing; tests for `isOverdue` edges (today, closed, null, zone boundary).

## 2.2 Sprints
**Data — `022_sprints.sql`**
- `sprints(id, project_id, name, goal, starts_on, ends_on, state planned|active|closed, created_by, started_at, closed_at, created_at)`.
- Partial unique index: one `active` sprint per project.
- `sprint_items(sprint_id, bug_id, added_at, added_by, removed_at, removed_by, carried_from_sprint_id)`: membership history, so scope change and carry-over are facts, not guesses.
- Permission `plan` added to the permission list, `onboarding.ts` presets (qa) and AI onboarding allowed list.

**Rules**
- A bug is in at most one open (planned/active) sprint at a time.
- Items added after `started_at` = **added scope**; items still open at close = **carried over** (moved to a chosen next sprint or back to backlog, each recorded with `carried_from_sprint_id`).
- Closed sprints are read-only.
- Only bugs inside the sprint's project; deleted (Trash) bugs drop out of counts but keep history.

**Server:** `createSprint`, `updateSprint`, `startSprint`, `closeSprint({ carryTo })`, `addToSprint`, `removeFromSprint`. All `plan`-gated, audited (`sprint.*`), request-ID idempotent.

**UI**
- `/admin/sprints`: list per project (planned / active / closed), create dialog (name, goal, dates).
- Sprint page: items table (reuses compact bug table), summary: committed, added, done, carried.
- "Add to sprint" in bug row menu and bulk bar.
- Member portals: read-only "Current sprint" tab for scoped projects.

**MCP:** `get_sprint` (active sprint of a project, compact text). No create/close via MCP in Phase 2.

**Done when:** start/close rules enforced server-side; carry-over visible on both sprints; one-active-sprint constraint holds under concurrent starts.

## 2.3 Scrum board
Columns follow the existing workflow, so the board **never bypasses transition rules**:

| Column | Statuses |
| --- | --- |
| To do | NEW, VALIDATING, VALIDATED, READY_FOR_ASSIGNMENT, NEEDS_INFORMATION, REOPENED |
| Assigned | ASSIGNED |
| In progress | IN_PROGRESS |
| Retest | RECHECK |
| Done | RESOLVED, DUPLICATE, NOT_A_BUG, WONT_FIX |

**Behaviour**
- Drag uses the existing status mutation: allowed drops are those where `canTransition` + `mayUpdateStatus` (or `statusPath`) permit; other columns dim while dragging.
- Drop into Assigned opens the assign dialog; drop into Done from Retest opens the verify dialog (RESOLVED only via verify). Cancel = card returns.
- Version conflict: card snaps back with "Changed by someone else, refreshed".
- Filters: sprint (default active), assignee, priority, "only mine". Card: code, title, priority, assignee avatars, due badge.
- Keyboard: pick up with Space, move with arrows (dnd-kit sensors). Board is view + existing actions only, no new permission.
- Phone width: columns become a horizontally swipeable single column; no page-level horizontal scroll.

**Route:** `/admin/board` + "Board" tab in developer and QA portals (scoped).

**Done when:** every drop either performs an allowed audited transition or is refused with a reason; a developer can only move their own assigned cards; tests for the column→status mapping and drop-permission helper.

## 2.4 Agile backlog
**Data — `023_work_items.sql`**
- `bugs.kind text not null default 'bug'` check in (`bug`, `story`, `task`, `epic`).
- `bugs.parent_id` (story/task → epic; task → story), same project, no cycles (checked in the rule and by trigger).
- `bugs.estimate smallint null` (story points), `bugs.ready boolean default false`, `bugs.backlog_rank text` (fractional rank strings, so a reorder writes one row).

**Workflow for non-bug kinds** (pure table in `bugflow.ts`, next to bug transitions):
TODO → IN_PROGRESS → IN_REVIEW → DONE, plus → TODO (reopen) and → WONT_DO. Bugs keep their 13-status workflow unchanged. Board columns map these too (To do / In progress / Retest = In review / Done).

**Rules**
- Create/edit stories, tasks and epics: Admin or `plan`. Members with `report` still only report bugs.
- Epic progress = done children / all children (estimates when present).
- Sprints accept stories, tasks and bugs; epics are not sprint items.

**UI**
- `/admin/backlog`: one ranked list per project, drag to reorder, kind icons, epic filter, ready toggle, estimate, "Move to sprint".
- Epic page: children with progress bar.
- Report dialog gains a kind switch for `plan` holders; counts/dashboards stay **bug-only** unless a view says otherwise (keeps Phase 1 numbers meaningful).

**MCP:** list/detail show kind and parent; `report_bug` stays bug-only.

**Done when:** existing bug flows, counts, exports and tests unchanged for `kind='bug'`; reorder is one-row writes; cycle prevention tested.

## 2.5 In-app user guide

- Sections per role: raise a bug (with media + mark-up), validate and assign, fix and send to retest, verify, manage members and portals, connect an AI client, sprints and board (after 2.2/2.3).
- Content: original text adapted from the marketing guide; screenshots from `Bug_board_marketing_media` copied in only when final (marketing assets stay out of `public/` until then).
- Done when every step in the guide matches the shipped UI labels.

## 3.1 Burndown & velocity
- No new tables: computed from `sprint_items` history + `status_history` (done = closed set / DONE).
- Burndown per day of the sprint (remaining count or points; added scope shown as a step up). Velocity = done points/items per closed sprint, last 6 sprints.
- Charts with `recharts` (installed) on the sprint page and Reports. Pure functions `burndown(sprint, events)`, `velocity(sprints)` with tests.
- **Done when:** chart totals equal the sprint page summary for the same sprint.

## 3.2 SLA timers
- `024_sla.sql`: `settings` key `sla` → targets per priority (P0–P5): respond-by (first move out of NEW) and fix-by (reach RECHECK/RESOLVED). Optional pause in NEEDS_INFORMATION.
- Rule `slaState(bug, history, now, targets)` → `ok | at_risk (≥80%) | breached`, computed on read, never stored.
- Badge in rows/board cards, Overview card "SLA at risk / breached", filter. Bell alert at risk + breach to assignees and Admin.
- **Done when:** paused time excluded; changing targets recalculates without migrations; tests for pause, reopen, priority change mid-flight.

## 3.3 Email / Slack / Teams alerts
- `025_alert_channels.sql`: `alert_channels(id, kind email|slack|teams, target_ciphertext, events jsonb, active, created_by)`; `alert_deliveries(id, channel_id, event_id, status, attempts, last_error, sent_at)` for retries and no duplicates.
- Sources = existing notification events (assignment, status change, mention, due/SLA); quiet `bug.media_*` stays excluded (`QUIET_ACTION_PREFIXES`).
- Slack/Teams via incoming webhook URLs (encrypted with `BUGFLOW_PORTAL_ENCRYPTION_KEY`); email via a transactional provider key in env (provider choice at build time; needs user approval of the account).
- Delivery runs in the existing throttled `sweep()` pattern, batched; per-member opt-out in their portal.
- Settings → Alerts: add channel, pick events, **Send test**. Messages carry links via `shareOrigin()`.
- **Done when:** a failed webhook retries with backoff and shows the error in Settings; no secret appears in logs or client bundle.

## 3.4 Releases & versions
- `026_releases.sql`: `releases(id, project_id, name, target_on, released_at, notes)`; `bugs.fixed_in_release_id`.
- Set "Fixed in" when verifying (verify dialog) or later by Admin/`plan`; audited.
- Release page: what's fixed, still open, carried; **Copy release notes** (Markdown, reuses export formatting).
- MCP: `list_release` (compact text).
- **Done when:** notes list only RESOLVED items in scope; a reopened bug drops out of "fixed" automatically.

## 3.5 GitHub / GitLab links
- `027_code_links.sql`: `code_integrations(id, provider, repo, webhook_secret_hash, token_ciphertext)`, `bug_code_links(bug_id, provider, kind commit|pr, url, title, state, merged_at)`.
- Link by bug code in branch/commit/PR title (e.g. `BUG-123`), parsed by a pure `findBugCodes(text)`.
- Webhook routes `/api/hooks/github`, `/api/hooks/gitlab` (signature verified, no cookies, `checkOrigin` not applicable as with MCP). PR merged → bug moves to RECHECK only if the current status allows it (`canTransition`), recorded as actor "GitHub (linked by Admin)".
- Bug detail: linked commits/PRs with state.
- **Done when:** unsigned or replayed webhooks are rejected; an auto-move never skips QA verification.

## 3.6 AI triage
- On new report (and on demand): server-only call via existing `AI_API_KEY` client; suggestions only — **never auto-applies** (same principle as AI onboarding).
- Suggests: likely duplicates (top 3 by text similarity among open scoped bugs, pre-filtered in SQL with `pg_trgm`, then AI ranks), severity, module, developer (from assignment history in that module).
- `028_triage.sql`: `bug_triage(bug_id, suggestions jsonb, model, created_at, accepted jsonb)`; enable `pg_trgm`.
- QA sees a "Suggestions" panel with Accept per item; Accept uses the normal audited mutations.
- Cost guard: one call per report, skip when AI is not configured, daily cap in Settings.
- **Done when:** with AI off, everything works unchanged; accepted vs ignored is recorded for tuning.

## 3.7 Phone capture
- Report form on phone width: camera/screenshot button (`capture` input), auto-filled device, OS, browser, screen size, app URL into environment (only facts read from the device, never invented).
- Optional PWA manifest so testers can add it to the home screen; upload goes through the existing queue.
- **Done when:** a report from a phone portal arrives with media + environment filled; desktop form unchanged.

## 3.8 Customer feedback widget
- `029_feedback.sql`: `feedback_sources(id, project_id, public_key, allowed_origins, active)`, `feedback_items(...)` into a **triage queue**, not directly into bugs.
- Embeddable `<script>` posting to `/api/feedback` (origin allow-list, rate limit per address, size limits, optional screenshot through a short-lived signed upload).
- QA turns an item into a bug (prefilled report) or dismisses it; AI triage (3.6) can suggest duplicates.
- **Done when:** unknown origins are refused; spam limits hold; no member or bug data is exposed to the public endpoint.

## 3.9 SSO & MFA
- Admin sign-in with Google / Microsoft (OIDC) mapped to the configured owner email; TOTP two-factor for password sign-in (secret encrypted, recovery codes hashed).
- `030_admin_mfa.sql`. Throttling and session rules unchanged; demo login must be removed first.
- Member portals stay link-based (optionally "require company sign-in" per member later).
- **Done when:** a wrong OTP is throttled like a wrong password; lost-device recovery works with a recovery code.
